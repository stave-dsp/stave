# DSP roadmap

The working ledger for stave-dsp: what the library models, how each
model is proven, how fast it runs, and the tools to design new
hardware with it. Like `OVERHAUL.md`, every line
is one piece of work with an id; tick it with the pull request that lands
it, as `PR #N (<merge commit>)`. The merge queue squashes, so a branch's own
commit hashes never reach main: cite the PR, never a branch commit.

## Goals

- **Composable, honest models.** A circuit model says which schematic
  it solves and is checked against SPICE or an independent reference.
  A behavioural model says what it was fitted to. Nothing in between
  claims to be "analog".
- **Every model has a verification loop.** A reference (ngspice,
  high-precision solution, hardware capture), an error budget, and a
  test that fails when the model drifts from it.
- **Every model has a cost.** ns/sample at the shipping rate,
  measured the same way everywhere, tracked over time.
- **Realtime-safe by construction.** No allocation, locks or unbounded
  loops on the audio thread. Solvers have iteration caps that are
  reported, never silent.
- **Pit of success.** Author-facing types make the wrong thing hard:
  units are types, sample rates are prepared once, nonlinear stages
  name their anti-aliasing.

## Architecture

The library grows to hundreds of models, so where a thing lives and what
it is called must answer three questions on sight: *what does it model*,
*how was it derived*, and *how is it verified*.

### Layers: a model lives where its claim lives

A model's location is the claim it makes, and the claim decides its
verification. Each layer depends only on the ones above it
(`scripts/check-view-bindings.sh` enforces it).

| Layer | Claim | Verified by |
|---|---|---|
| `units` | quantities as types (`Hz`, `Db`, `Seconds`, `Ohms` …) | unit tests, Kani |
| `kernel` | the `Stage` contract and graph forms (serial, parallel, loop, oversampling, voices, lanes) | property tests, loom, Kani |
| `primitives` | textbook DSP: filters (linear, the Hilbert pair, and the published nonlinear filter structures — ladders, Sallen–Key, Korg35 — with their saturators), delays and interpolation, spectral (FFT, convolution, STFT, FIR design), oscillators, control | naive references (direct DFT, direct convolution, analytic responses); a structure that reduces a circuit, also that circuit's netlist through `Circuit<Dk>` |
| `behavioral` | a shape chosen or fitted, with **no hardware claim**: named by its maths (`Tanh`, `Knee`, `Fold`) and its anti-aliasing | analytic antiderivatives, aliasing budgets |
| `circuit` | derived from a schematic | ngspice on the same netlist (R1–R4) |
| `physical` | derived from mechanics or acoustics: springs, plates, rotors, tape transport, speakers, rooms, instruments | published modes, high-precision solutions, captures |
| `learned` | trained from captures: WaveNet, LSTM, Wiener–Hammerstein | parity with the reference implementation, capture error |
| `effects` | algorithmic designs that model no hardware: reverbs (FDN, Dattorro), pitch, granular, dynamics, EQ | analytic properties, golden audio |
| `structures` | compositions: `Chain`, `ModMatrix` | property tests |

A circuit and the structure it reduces to are two claims, so two
places: the Moog transistor ladder's netlist
(`circuit::topologies::transistor_ladder`, held to ngspice) is the
truth, and Huovilainen's four-`tanh` model of it
(`primitives::filters::ladder::Huovilainen`, a published structure,
held to the netlist's ngspice run) is the cost.

So a "diode" can appear three ways, and each is obvious from its path:

```text
circuit::devices::diode::Shockley          the junction equation (a device model)
circuit::topologies::diode_clipper()       a netlist that uses it
behavioral::shapes::Tanh                   a curve a designer may choose instead — no diode claim
learned::WaveNet                           a capture of a real clipper pedal
```

### Inside `circuit`: devices, methods, netlists, topologies

Four separate concerns, so any circuit can be solved any supported way:

```text
circuit/
  devices/      one module per device family; one type per published model
    diode/        Shockley (+ series R as a field); parts as consts: Shockley::N4148, Shockley::N34A
    bjt/          EbersMoll, GummelPoon;  parts: GummelPoon::BC109, ::AC128
    jfet/  mosfet/  triode/ (Koren, Dempwolf, CohenHelie)  pentode/ (Koren, CohenHelie)
    opamp/ (Ideal, Macromodel)  ota/  photocell/  magnetic/ (JilesAtherton)
  netlist/      Netlist, Element, Node; SPICE-subset and KiCad import
  methods/      how a circuit is solved
    newton/  wdf/ (elements, adaptors incl. RType)  dk/ (nodal DK state space)
    table/   wright_omega/  load_line/  hamiltonian/
  topologies/   named circuits as netlists (data, not code): tube_screamer(),
                fuzz_face(), marshall_tone_stack() … each with its ngspice case
  Circuit<M>    one runtime type: a netlist solved by method M
```

- A **device family** has one trait (`Diode`, `Bjt`, `Triode` …) that every
  model of it implements, so a circuit can swap `Koren` for `Dempwolf`.
- **Parts** are constants of a model's parameters, named by part number,
  never separate types.
- The **method is a type parameter**, not part of a name:
  `Circuit::<Dk>::new(fuzz_face())`, `Circuit::<Wdf>::new(..)`. Each method
  documents which netlists it accepts (WDF needs adaptable structure; DK
  takes any MNA-solvable netlist). A hand-optimised topology may exist as
  its own type when it is measurably faster, and it is then checked
  against `Circuit<Dk>` on the same netlist.

### Naming rules

1. **Name the thing, not the implementation.** No `Model`, `Impl`,
   `Processor`, `Engine`, `Helper`, `V2`, `New`, `Simple`, `Fast`
   suffixes or prefixes.
2. **The approach lives in the path or a type parameter**, never in a
   compound name: `devices::diode::Shockley`, not `ShockleyDiodeModel`;
   `Convolver::uniform(..)`, not `UniformPartitionedConvolver`.
3. **Published models are named after their model or authors** (`Koren`,
   `EbersMoll`, `GummelPoon`, `Huovilainen`, `JilesAtherton`, `Dattorro`);
   **parts after part numbers** (`N4148`, `BC109`, `MN3007`); **shapes after their
   maths** (`Tanh`, `Knee`, `Chebyshev`).
4. **Module names are plural for peer collections** (`devices`, `methods`,
   `topologies`, `filters`, `shapes`) and singular for one concept
   (`netlist`, `spectral`, `units`).
5. **The crate root re-exports only author-level vocabulary**: the `Stage`
   contract, units, the common primitives and effects. Model families are
   reached by path, so `triode::Koren` and `pentode::Koren` never collide
   and the path always says what a thing is.
6. **One concept per file**, tests beside it (`foo.rs` + `foo/tests.rs`),
   within the repo's file-size limit.
7. **Every public model's rustdoc has the same sections**: *Models* (what
   hardware or maths), *Derivation* (schematic, measurement, training,
   textbook), *Verified* (the test that holds it to its reference, and the
   budget), *Cost* (its datasheet line), *Aliasing* (none, ADAA, or the
   oversampling it expects), *Valid ranges*. A docs-site page, the **model
   catalogue**, is generated from these, and the build fails when a public
   model lacks a section or names a test that doesn't exist.

## Measurement design

What we measure decides what we can claim. The aim is the richest picture
of a model per CPU-second, held to three references:

- **The equations** — ngspice and high-precision solutions. Proves we solve
  the model; available for every circuit, automated.
- **The ear** — most models are voiced by listening, because hardware is
  not at hand for most of what we build. Voicing is a first-class,
  structured activity (level-matched A/B, blind ABX, recorded decisions),
  and its result is pinned as a fingerprint so a voiced sound never drifts
  by accident.
- **Program material** — real instruments from the user's sample library,
  so every model is heard and measured on the material it will process.

Hardware captures, where a unit is available, join as a fourth reference.
Every model, circuit and plugin is measured with the *same* stimulus suite,
so results compare across models, across commits and, when they exist,
against captures.

### Principles

1. **Coherent sampling.** Every steady-state tone sits exactly on an FFT bin
   (`f = k·fs/N`, the run an integer number of periods), so one rectangular
   window gives exact magnitudes and phases with zero leakage — no averaging,
   no windows, the shortest possible run. `k` is chosen so that harmonics
   2…H, their aliases above Nyquist, and intermodulation products each land
   on a distinct empty bin: harmonics, aliases and noise separate exactly.
2. **Multisine first.** One run of a sparse odd-odd multisine (tones on bins
   ≡ 1 mod 4, log-spaced, Schroeder or random phases for a low crest factor)
   yields, per frequency, the best linear approximation (magnitude **and**
   phase) plus the even- and odd-order distortion falling on the unexcited
   detection bins (Pintelon & Schoukens). That replaces dozens of single-tone
   runs with one.
3. **Levels relative to the circuit, not absolute.** A quick DC/level sweep
   finds each circuit's knee (input for 1 dB compression, or 1 % THD at 1
   kHz). Nonlinear measurements then run at fixed offsets from the knee —
   −40, −20, −10, −3, 0, +6, +12, +20 dB — so "clean", "edge of breakup" and
   "full saturation" mean the same thing for a fuzz and a mastering
   limiter. Real-world anchors are measured too, at calibrated levels:
   instrument (single coil ~100 mV, hot humbucker ~1 V peak, a dug-in pick
   ~2 V peak), line (−10 dBV, +4 dBu, +24 dBu hot), and the plugin's 0 dBFS
   calibration.
4. **Periodic steady state, not long settling.** Start from the solved
   operating point (DK has it), discard settling periods computed from the
   circuit's slowest time constant, and accept the run when the last two
   periods agree to the budget — measured, not guessed, settling.
5. **Separate the questions.** Solver correctness (vs ngspice) runs
   oversampled where numerical error is tiny; shipping behaviour runs at
   44.1/48/96 kHz with the plugin's own oversampling, with its own budget.
   Both are reported.
6. **Budgets that mean something.** Errors are judged relative to what is
   audible: harmonic errors in dB relative to that harmonic (with an
   absolute floor below −120 dBc), response errors in dB and degrees,
   residuals by noise-to-mask ratio (NMR) against a psychoacoustic masking
   model, never only by waveform RMS.

### Refinements from the literature

From the measurement survey (sources cited in the local research index):

- **Multisine phases by purpose.** The best linear approximation depends on
  the stimulus's amplitude distribution, so random-phase and Schroeder
  multisines are not interchangeable (Schoukens, Vaes & Pintelon 2016). C3
  uses random phases; Schroeder only to cross-check C4. Fingerprints record
  the phase law and seed.
- **Realisations, not one run.** Distortion that varies with the random-phase
  draw cannot be separated from the BLA in one run: T1 averages M ≥ 4
  realisations of one period each (M = 8 at T2); a T0 single run is labelled a
  single-realisation response.
- **Grids.** Random-odd quasi-logarithmic excitation (Vanhoenacker et al.
  2001) with detection lines between consecutive excited lines and at least 3
  excited lines per octave. Coherent tones use cycle counts coprime with the
  record length (IEEE 1241).
- **Levels by RMS.** "Re knee" is defined by RMS, and each stimulus's crest
  factor is stored (random-phase multisines run ~10–12 dB against a sine's 3).
- **Synchronized swept sine** (Novak et al. 2015), with its length rule, so
  harmonic phases are right; sized from the stage's memory (≈0.6 s for order 5,
  ≈2 s for order 15 at a 20 ms response; longer for tape, reverb, magnetics),
  run at ≥ 3 levels with kernels checked for consistency.
- **IMD details.** SMPTE tones moved onto coherent bins within RP120's ±3 %,
  sidebands 7 kHz ± n·60 Hz (n = 1…6) summed. CCIF 19 + 20 kHz doubles as an
  alias detector at 44.1/48 kHz (the sum product folds in-band), reported
  separately.
- **Weighting stated.** Every THD+N and noise figure states its bandwidth
  (AES17 20 kHz) and weighting (A, ITU-R 468).
- **Aliasing budget by audibility:** A-weighted noise-to-mask ratio ≤ −10 dB
  (Lehtonen et al. 2012; Kahles et al. 2019), swept every semitone from
  27.5 Hz to 4186 Hz at +12 and +20 dB re knee at T1.
- **Perceptual distortion metric.** THD/IMD correlate with perceived
  distortion only at |r| ≈ 0.45; Rnonlin reaches ≈ 0.95 (Moore 2020): add it,
  and the GedLee metric on static transfer curves. NMR per BS.1387 (as
  implemented by Kabal), not the PEAQ quality score; playback level recorded
  (default 92 dB SPL).
- **Phase budgets.** Group delay |Δ| ≤ 0.2 ms from 500 Hz to 4 kHz (threshold
  ≈ 0.6 ms, Liski et al. 2021); interchannel delay ≤ 10 µs (image shifts at
  ≈ 35 µs, Møller et al. 2007).
- **Listening statistics.** ABX defaults to ≥ 40 trials (16 trials at a true
  hit rate of 0.7 detect only 45 % of the time; Leventhal 1986), logs p, power
  and d′, and never records "inaudible" from a short run. Voicing matches
  loudness to ≤ 0.1 LU, with anchors and bias controls (BS.1534, Zielinski et
  al. 2008); BS.1116 for near-threshold questions.
- **Reproducible metrics.** Metric implementations are versioned in
  fingerprints; the BS.1387 conformance items and EBU Tech 3341 loudness
  vectors run as T0 tests.
- **Model error.** ESR is reported only with A-weighted pre-emphasis and
  beside perceptual metrics (Wright & Välimäki 2020).
- **Corpus.** Edge-of-breakup DI exposes model differences best: the DI set
  includes it.

### Characteristics

| # | Characteristic | Stimulus | Reveals |
|---|---|---|---|
| C1 | Operating point | none (DC) | bias, headroom, asymmetry source |
| C2 | Small-signal response, magnitude + phase + group delay | multisine at −40 dB re knee, or linearisation | tone, bandwidth, phase character |
| C3 | Best linear approximation vs level | odd-odd multisine at each level | how tone changes as it is driven |
| C4 | Compression / gain vs level | stepped coherent sine (1 kHz, plus 100 Hz and 5 kHz) | headroom, knee shape, softness |
| C5 | Harmonics H2–H15, magnitude **and** phase, per level × frequency | coherent sines at 82, 330, 1k, 3k, 8k Hz × the level grid | the character itself: even/odd balance, waveform asymmetry |
| C6 | THD+N and noise floor | same runs; idle run | grit, hiss, noise modulation |
| C7 | Intermodulation | SMPTE (60 Hz + 7 kHz, 4:1), CCIF (19 + 20 kHz), and multisine detection bins | muddiness, chord behaviour, high-frequency aliasing |
| C8 | Dynamics | tone bursts (5 ms–500 ms on, at +6/+20 dB re knee), level steps, a synthetic pluck envelope | sag, bias shift, blocking distortion, attack/release, time-varying harmonics |
| C9 | Hysteresis / memory | slow triangle and level ramps up vs down | magnetics, tape, opto, thermal |
| C10 | Aliasing at the shipping rate | coherent sines whose aliases fall on empty bins; a log sweep up to Nyquist | digital artefacts — where cheap emulations lose |
| C11 | Sample-rate invariance | C2/C5 at 44.1, 48, 88.2, 96, 192 kHz | the same sound at every host rate |
| C12 | Volterra / Hammerstein kernels | exponential sine sweep (Farina), 0.5–2 s | a compact fingerprint of weak nonlinearity; fits grey-box models |
| C13 | Program material | short owned recordings: guitar DI, bass DI, drums, vocal, mix bus | the final check, by NMR on the null residual |

| Tier | When | What | Target time |
|---|---|---|---|

Reference data is generated offline (ngspice, captures) and committed as
compact tables — harmonic magnitudes/phases, response points, compression
curves — never as long waveforms. Tests only compare.

### Fingerprints

Each model, circuit and plugin has a committed **fingerprint**: its T0/T1
results as data. CI diffs fingerprints, so any change in sound — even one
that passes every budget — is visible in review, and an intended change is
re-blessed on purpose. The model catalogue and plugin pages show the
fingerprints as plots: frequency response, harmonic spectra against level,
compression curves, aliasing, with the reference overlaid. No plugin
vendor publishes this; we can.

### Voicing by ear

Most models are tuned by listening. The tooling makes that rigorous:

- **Audition in stave-play** against a reference — another model, an
  earlier fingerprint, a capture when one exists, or bypass — always
  **loudness-matched** (LUFS), since louder reads as better.
- **Blind ABX and preference trials** with randomised order, logged per
  session with the settings, program material and verdicts, so a voicing
  decision has a record and can be revisited.
- **Measured targets where no capture exists:** published datasheet curves
  (tube plate curves, transistor families, op-amp slew), published
  frequency responses of classic circuits, and the designer's own target
  curves, as reference tables in the same format as ngspice data.
- **Pinning the result:** once a sound is chosen, its fingerprint (C2–C10
  at the control corners) is blessed, so later refactors that change it
  fail review instead of silently drifting from what was chosen by ear.

### Reference program material

From the sample library named by `STAVE_SAMPLE_LIBRARY` (local configuration;
see `stave.env.example`). The maintainer's library holds:

- `Test Corpus/` — 58 deterministic 48 kHz/24-bit picks in 13 sets (drum
  loops, kicks, snares, hats, percussion, piano and synth notes, vocals and
  vocal phrases, tonal loops, textures, fx, guitar), curated for stave.
- `Stems/` — real multitracks (guitars, bass, drums, vocals in context).
- Clean **DI guitar and bass** for amps, pedals and cabs — a gap today
  (the `guitar_di` and `bass_di` roles are empty). Searched 2026-11-13:
  nothing in the manifest is a dry DI. The Test Corpus guitars are amped
  loops; every guitar stem is stereo with differing sides and rolls off
  like a miked cab (−35 to −50 dB at 4–6 kHz re 200 Hz–2 kHz); the
  "DI"/"dry"/"clean" names are drums, a sidestick, and one-shot AIFF
  notes. Closest: a stem's mono `BASS CLEAN`, the clean side of a split
  bass, held as `bass_clean` and not counted as a DI. The fill is cheapest
  recorded: mono, 48 kHz/24-bit, the interface's instrument input, no
  processing, peaks −12 to −6 dBFS, into `Source Material/DI/Guitar` and
  `Source Material/DI/Bass` — guitar (about 4 min): single-coil neck
  single notes with bends (30 s); single-coil strummed open chords left
  to ring (30 s); bridge humbucker palm-muted low-string chugs, 8ths to
  16ths (30 s); humbucker sustained power chords (30 s); humbucker lead,
  legato and vibrato (30 s); edge of breakup, soft fingerpicking building
  to hard pick attack (30 s); drop-tuned chugs (30 s); 10 s plugged in,
  volume up, not played (hum and noise). Bass (about 2 min):
  fingerstyle line (30 s); picked 8ths (30 s); slap and pop (20 s); low
  notes left to decay into silence (20 s). If the stems' own sessions
  kept DI tracks, exporting them fills the roles too.

The audio is never committed (its licences allow use, not redistribution).
A committed spec (`crates/stave-test/corpus.spec`) names what the checks
need by role — guitar DI, bass DI, amped guitar, drum loops and stems,
transients, a mix bus of summed stems, vocal, piano, synth pads and notes,
tonal loops, textures, fx — with the rules that pick each from the
library (`_corpus.json` sets, `_manifest.csv` categories, directories,
length, rate; WAV only, never AppleDouble sidecars or AIFF). A local lock
(`scripts/corpus.sh lock`, never committed) records each pick's SHA-256,
so a run plays exactly what the lock names and fails on drift;
`scripts/corpus.sh check` reports missing roles and drift without copying
anything. `STAVE_SAMPLE_LIBRARY` points at the library; tests that need it
run when it is present (on the machine with the drive, or a synced copy on
a build host) and report "skipped: library absent" otherwise. Program-material
results (C13) are judged by NMR on the null residual against the pinned
fingerprint or reference (`stave_test::corpus::c13`), and auditioned.

### Hardware captures (when a unit is available)

The same stimulus suite (C2–C12) is played through the real unit with a
reamp/interface rig, calibrated in volts (dBu), with loopback compensation
of the interface's own response and latency, at every control corner
(C14). Captures live outside git with checksums committed (R8) and join the
other references; a model with a capture is held to it within budget.

## Order

1. **F1–F2** (FFT, convolution) and **R1–R2** (one reference harness,
   ngspice in CI): the most-used gap and the loop everything else
   is verified with. Then **K1–K6** (architecture), before new families land.
2. **R17–R19** (the measurement design: stimulus suite, characterisation
   matrix, fingerprints, NMR) — every model after this is born measured.
   **N1–N3** (netlist, DK method, solve strategies) with **R3–R4**.
3. **U1–U5** (unit types), before the library grows further, so new APIs
   are born typed.
4. **E1–E6** (BJT, FET, pentode, op-amp, OTA, diode presets) on N2.
5. **A1–A4** and **R5** (anti-aliasing for circuits, with budgets).
6. **P1–P3, P5** (datasheet as data, deterministic perf CI, flamegraphs).
7. **M1–M4** (neural inference, grey-box, capture).
8. **S1–S7**, **D1–D4**.
9. **H1–H9** (hardware beyond circuits) and **G1–G5** (design tools).
10. The exploratory items: **N7**, **M5**, **M6**, **E10**, **H10**.
