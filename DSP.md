# DSP roadmap

The working ledger for stave-dsp: what the library models, how each
model is proven, how fast it runs, and the tools to design new
hardware with it. Like `OVERHAUL.md`, every line
is one piece of work with an id; tick it with the commit that lands it.

## Goals

- **Composable, honest models.** A circuit model says which schematic
  it solves and is checked against SPICE or an independent reference.
  A behavioural model says what it was fitted to. Nothing in between
  claims to be "analog".
- **Every model has a verification loop.** A reference (ngspice,
  high-precision solution, hardware capture), an error budget, and a
  test that fails when the model drifts from it.
- **Every model has a cost.** ns/sample at the shipping rate,
  measured the same way everywhere, tracked over time.
- **Realtime-safe by construction.** No allocation, locks or unbounded
  loops on the audio thread. Solvers have iteration caps that are
  reported, never silent.
- **Pit of success.** Author-facing types make the wrong thing hard:
  units are types, sample rates are prepared once, nonlinear stages
  name their anti-aliasing.

## What exists today (v0.4.0)

- **Circuit** (`circuit/`):
  - devices: Shockley diode, triodes (Koren, Dempwolf), Jiles–Atherton core;
  - methods: Newton with SPICE junction limiting, Wright omega,
    load lines, WDF with series/parallel adaptors;
  - topologies: diode clipper, op-amp clipper, common cathode,
    triode stage, coupler, tone stack (Yeh–Smith), power supply, push-pull,
    transformer.
  - Ten circuits are checked against ngspice (`stave-test/tests/matches_ngspice.rs`,
    netlists in `stave-test/spice/`, regenerated by `scripts/ngspice-simulate.py`).
  - The magnetic models are checked against high-precision solutions
    (`matches_reference.rs`, `scripts/ja-reference.py`).
  - Every Newton topology converges under its cap at the host rate
    (`solver_conformance.rs`).
- **Behavioural** (`behavioral/`): ADAA (1st and 2nd order, memoryless
  shapes), tabulated curves, shapes (knee, asym, fold, Chebyshev), smooth
  saturation, slew, hysteresis, nonlinear RC.
- **Primitives**: f64 biquad, ZDF SVF, one-pole, allpass, Linkwitz–Riley
  crossovers, delay line, comb, polyBLEP oscillator, LFO, ADSR, envelope,
  random, smoothing.
- **Kernel**: 2×/4× linear-phase oversampling, resampling, voices, lanes,
  feedback, parallel, sequence.
- **Measurement** (`stave-measure`): levels, loudness (peak, true peak, RMS,
  LUFS), spectrum (FFT, Goertzel), THD/THD+N, latency, transfer functions,
  tails, zipper, stereo, dynamics.
- **Cost**: `stave-dsp/tests/datasheet.rs` prints ns/sample per primitive
  (documents, never blocks); `stave-bench` measures a built plugin.

## Architecture

The library grows to hundreds of models, so where a thing lives and what
it is called must answer three questions on sight: *what does it model*,
*how was it derived*, and *how is it verified*.

### Layers: a model lives where its claim lives

A model's location is the claim it makes, and the claim decides its
verification. Each layer depends only on the ones above it
(`scripts/check-view-bindings.sh` enforces it).

| Layer | Claim | Verified by |
|---|---|---|
| `units` | quantities as types (`Hz`, `Db`, `Seconds`, `Ohms` …) | unit tests, Kani |
| `kernel` | the `Stage` contract and graph forms (serial, parallel, loop, oversampling, voices, lanes) | property tests, loom, Kani |
| `primitives` | textbook linear DSP: filters, delays and interpolation, spectral (FFT, convolution, STFT, FIR design), oscillators, control | naive references (direct DFT, direct convolution, analytic responses) |
| `behavioral` | a shape chosen or fitted, with **no hardware claim**: named by its maths (`Tanh`, `Knee`, `Fold`) and its anti-aliasing | analytic antiderivatives, aliasing budgets |
| `circuit` | derived from a schematic | ngspice on the same netlist (R1–R4) |
| `physical` | derived from mechanics or acoustics: springs, plates, rotors, tape transport, speakers, rooms, instruments | published modes, high-precision solutions, captures |
| `learned` | trained from captures: WaveNet, LSTM, Wiener–Hammerstein | parity with the reference implementation, capture error |
| `effects` | algorithmic designs that model no hardware: reverbs (FDN, Dattorro), pitch, granular, dynamics, EQ | analytic properties, golden audio |
| `structures` | compositions: `Chain`, `ModMatrix` | property tests |

So a "diode" can appear three ways, and each is obvious from its path:

```text
circuit::devices::diode::Shockley          the junction equation (a device model)
circuit::topologies::diode_clipper()       a netlist that uses it
behavioral::shapes::Tanh                   a curve a designer may choose instead — no diode claim
learned::WaveNet                           a capture of a real clipper pedal
```

### Inside `circuit`: devices, methods, netlists, topologies

Four separate concerns, so any circuit can be solved any supported way:

```text
circuit/
  devices/      one module per device family; one type per published model
    diode/        Shockley (+ series R as a field); parts as consts: Shockley::N4148, Shockley::N34A
    bjt/          EbersMoll, GummelPoon;  parts: GummelPoon::BC109, ::AC128
    jfet/  mosfet/  triode/ (Koren, Dempwolf, CohenHelie)  pentode/ (Koren, CohenHelie)
    opamp/ (Ideal, Macromodel)  ota/  photocell/  magnetic/ (JilesAtherton)
  netlist/      Netlist, Element, Node; SPICE-subset and KiCad import
  methods/      how a circuit is solved
    newton/  wdf/ (elements, adaptors incl. RType)  dk/ (nodal DK state space)
    table/   wright_omega/  load_line/  hamiltonian/
  topologies/   named circuits as netlists (data, not code): tube_screamer(),
                fuzz_face(), marshall_tone_stack() … each with its ngspice case
  Circuit<M>    one runtime type: a netlist solved by method M
```

- A **device family** has one trait (`Diode`, `Bjt`, `Triode` …) that every
  model of it implements, so a circuit can swap `Koren` for `Dempwolf`.
- **Parts** are constants of a model's parameters, named by part number,
  never separate types.
- The **method is a type parameter**, not part of a name:
  `Circuit::<Dk>::new(fuzz_face())`, `Circuit::<Wdf>::new(..)`. Each method
  documents which netlists it accepts (WDF needs adaptable structure; DK
  takes any MNA-solvable netlist). A hand-optimised topology may exist as
  its own type when it is measurably faster, and it is then checked
  against `Circuit<Dk>` on the same netlist.

### Naming rules

1. **Name the thing, not the implementation.** No `Model`, `Impl`,
   `Processor`, `Engine`, `Helper`, `V2`, `New`, `Simple`, `Fast`
   suffixes or prefixes.
2. **The approach lives in the path or a type parameter**, never in a
   compound name: `devices::diode::Shockley`, not `ShockleyDiodeModel`;
   `Convolver::uniform(..)`, not `UniformPartitionedConvolver`.
3. **Published models are named after their model or authors** (`Koren`,
   `EbersMoll`, `GummelPoon`, `Huovilainen`, `JilesAtherton`, `Dattorro`);
   **parts after part numbers** (`N4148`, `BC109`, `MN3007`); **shapes after their
   maths** (`Tanh`, `Knee`, `Chebyshev`).
4. **Module names are plural for peer collections** (`devices`, `methods`,
   `topologies`, `filters`, `shapes`) and singular for one concept
   (`netlist`, `spectral`, `units`).
5. **The crate root re-exports only author-level vocabulary**: the `Stage`
   contract, units, the common primitives and effects. Model families are
   reached by path, so `triode::Koren` and `pentode::Koren` never collide
   and the path always says what a thing is.
6. **One concept per file**, tests beside it (`foo.rs` + `foo/tests.rs`),
   within the repo's file-size limit.
7. **Every public model's rustdoc has the same sections**: *Models* (what
   hardware or maths), *Derivation* (schematic, measurement, training,
   textbook), *Verified* (the test that holds it to its reference, and the
   budget), *Cost* (its datasheet line), *Aliasing* (none, ADAA, or the
   oversampling it expects), *Valid ranges*. A docs-site page, the **model
   catalogue**, is generated from these, and the build fails when a public
   model lacks a section or names a test that doesn't exist.

### F — FFT, convolution, spectral

- [x] **F1** (e2fc31d: our own, `stave_dsp::Fft` — rustfft measured 1.6–3.3× faster, short of 10×; resample, the triode tests, stave-measure, stave-face and stave-play use it; the plugin copies migrate after the next release) One real FFT for the workspace, either our own (radix-2/4 split, power-of-two,
  f32 and f64) or a vetted dependency, behind one `Fft` type. It replaces the eleven
  plugin copies and `primitives/resample.rs`'s local radix-2.
- [x] **F2** (7b3cf69: `Convolver::uniform` with an `ImpulseResponse`, mono/stereo/true-stereo, latency one partition or zero with `Head::Direct`) Uniform partitioned convolution (overlap-save, frequency-domain
  delay line), zero allocation after `prepare`, any IR length.
- [x] **F3** (this commit: `Convolver::non_uniform(&ir, block, largest, head)`: power-of-two sizes up to `largest`, counts by dynamic programming over a measured cost model (García); 96 k taps at zero latency 68 ns/sample against 132 for uniform at a 256-sample latency) Non-uniform partitioned convolution (Gardner / Garcia
  schedules) for long IRs at low latency; worker-thread tail partitions
  with a lock-free handoff.
- [ ] **F3b** The worker-thread half of F3: the large partitions' steps
  computed off the audio thread (or spread over their block), handed
  back lock-free, so the worst block costs what the average does (today
  1.2 µs/sample against 68 average for 96 k taps). The schedule search
  must then keep one block of slack (`skip ≥ 1`) on the runs it moves;
  tests stay deterministic by running the worker inline.
- [ ] **F4** `ImpulseResponse` loading: WAV, resampled to the prepared
  rate, normalised, mono/stereo/true-stereo; minimum-phase conversion.
- [ ] **F5** STFT (analysis/synthesis with COLA windows) as a stage, the
  base for spectral effects and the phase vocoder (S6).
- [ ] **F6** Linear-phase and minimum-phase FIR design (windowed sinc,
  Parks–McClellan or least squares) as a library, used by F2's EQ and A3.

### N — circuit solvers

- [x] **N1** (c2c2a54) A netlist type in Rust: nodes, elements (R, C, L, sources,
  devices), and a parser for the SPICE subset `stave-test/spice/*.cir`
  already uses, so one netlist feeds both ngspice and stave.
- [ ] **N2** Nodal DK method (Yeh 2009; Holters & Zölzer 2015, ACME.jl):
  MNA → discretised state-space with the nonlinear subsystem separated,
  matrices computed once per prepare. Newton on the nonlinear subsystem
  only. Built from N1 netlists.
- [ ] **N3** Nonlinear solve strategies for N2: damped Newton with junction
  limiting (exists, generalise it), homotopy / source stepping for hard starts,
  a warm start from the previous sample, and an optional precomputed
  solution table with interpolation (and its error bound) for low-cost runtime.
- [ ] **N4** WDF R-type adaptors (Werner et al. 2015) via the scattering
  matrix from MNA, so non-tree topologies (bridged-T, tone stacks,
  multiple nonlinearities through SIM/multi-port roots) are expressible.
- [ ] **N5** WDF element set: inductor, ideal/resistive voltage and current
  sources, switches, short/open, polarity inverter, ideal transformer,
  op-amp (Paiva, Kemper) as roots or adaptors.
- [ ] **N6** Parameter changes in a running circuit: re-adapting port
  resistances and recomputing DK matrices without clicks, with smoothing
  and a bounded cost per block.
- [ ] **N7** (exploratory) Port-Hamiltonian formulation (Falaize & Hélie):
  energy-preserving discretisation with a passivity guarantee, checked
  against N2 on shared netlists.
- [ ] **N8** Health telemetry for every solver: iterations per sample,
  cap hits, residual, published as taps (P5), so a model that struggles
  at some setting shows it in a DAW.

- [ ] **E5** OTA (CA3080, LM13700) with tanh transconductance and bias

- [ ] **E6** Diode presets beyond Shockley defaults: 1N4148, 1N34A

### A — anti-aliasing and rates

- [ ] **A1** ADAA for stateful nonlinearities (Holters 2019) and inside
  WDF one-ports (Albertini et al. 2020), so circuits get the anti-aliasing
  memoryless shapes already have.
- [ ] **A2** Arbitrary-ratio oversampling (3×, 6×, 8×) and an IIR
  minimum-phase half-band option for low latency, with the latency
  reported exactly.
- [ ] **A3** Oscillators: BLAMP for triangle/hard sync, minBLEP option,
  wavetable with mip-mapped band limiting.
- [ ] **A4** An aliasing measurement in stave-measure (inharmonic energy
  of a swept tone through a stage, in dB below the fundamental) and a
  per-stage budget enforced in tests (R5).

### M — learned and grey-box models

- [ ] **M1** Neural inference engine: WaveNet (dilated conv, gated
  activations) and LSTM/GRU, f32 with SIMD, zero allocation in `process`,
  sample-rate handling via A2. Load Neural Amp Modeler `.nam` files.
  Check the format's licence terms before shipping a loader.
- [ ] **M2** Parity tests for M1 against the reference implementation's
  output on shared models and inputs (bit-close, with an error budget).
- [ ] **M3** Block-oriented models: Wiener, Hammerstein,
  Wiener–Hammerstein (linear filters around a static curve), with a
  fitting tool in `tools/` that captures from a plugin or audio pair.
- [ ] **M4** Capture workflow: a stimulus (ESS sweeps, multitone, noise
  bursts, real program material) and alignment/latency compensation, to
  fit M3 or train M1 out of tree (training stays in Python; inference in Rust).
- [ ] **M5** (exploratory) Differentiable grey-box: circuit-structured
  models with learned parameters (Kuznetsov et al. 2020), trained out of
  tree, inferred by N2/M3 stages.
- [ ] **M6** (analysis only) Volterra / generalised Hammerstein kernels
  identified from ESS (Farina) to *characterise* a model's or device's
  weak nonlinearity in reports; not a runtime model.

### S — structures and effects

- [ ] **S1** Nonlinear ZDF ladder (Moog, Huovilainen/Zavalishin), diode

- [ ] **S2** Fractional delay interpolation: Lagrange (3rd/5th), Thiran

- [ ] **S4** Hilbert transform (IIR allpass pair), frequency shifter,

- [ ] **S5** Linear-phase and dynamic EQ on F2/F6.
- [ ] **S6** Pitch: phase vocoder on F5, PSOLA, granular engine with

- [ ] **S7** Formant and vowel filters; comb/Karplus–Strong resonators as

### D — dynamics

- [ ] **D2** Gain computers: hard/soft knee, ratio, feed-forward and

- [ ] **H1** Bucket-brigade delay lines (MN3007/3205, MN3008): clocked

- [ ] **H2** Spring reverb: dispersive waveguides with chirp allpass

- [ ] **H4** Rotary speaker: horn and drum rotors with Doppler, amplitude

- [ ] **H5** Tape transport: wow and flutter as measured spectra, speed

- [ ] **H6** Controls as hardware: potentiometer tapers (linear, audio,

- [ ] **H7** Cabinet, microphone and room: IR-based (F2–F4) with mic

- [ ] **H8** Vintage digital: converter quantisation and dither, low and

- [ ] **H9** Noise and drift: thermal and shot noise sources tied to

- [ ] **H10** (instruments) Physical models: waveguide strings and tubes,

### G — design tools

- [ ] **G1** Schematic input: import a KiCad netlist (and the SPICE subset
  of N1) so a circuit designed in a schematic editor runs in stave.
- [ ] **G2** Sweeps and sensitivity: run any model over a parameter or
  component grid and report the response change per part (which resistor
  moves the tone most), as data and docs-site plots.
- [ ] **G3** Monte Carlo over tolerances (E10): the spread of response
  across built units, to choose part grades.
- [ ] **G4** Fitting: optimise component values or behavioural parameters
  to a target (a frequency response, a capture, a curve), with the fit
  error reported against the R1 budget format.
- [ ] **G5** Audition: design-time A/B and null tests against a reference
  (capture or another model), level-matched, with a blind ABX mode in
  stave-play.

  maths, partition schedules, interpolator weights sum to one).

### P — profiling and performance

- [ ] **P1** The datasheet as data: `datasheet.rs` writes JSON
  (ns/sample, spread, rate) per stage; the docs site shows it as a
  reference page, the same way the catalogue is generated.
- [ ] **P2** Deterministic performance regression in CI: instruction
  counts (iai-callgrind / cachegrind on Linux) per stage, with a
  committed baseline and a threshold, since wall clock on shared runners
  is noise.
- [ ] **P3** `scripts/profile.sh`: a flamegraph of any stage or plugin
  (samply on macOS, perf on Linux), opening the result.
- [ ] **P4** SIMD: portable lanes (`std::simd` when stable, or a narrow
  internal abstraction) for FFT, convolution, FIR and the M1 engine; the
  cost shown in P1 before and after.
- [ ] **P5** Per-stage cost and solver health (N8) as telemetry taps, so
  `stave-play` and a DAW session show where time goes.
- [ ] **P6** Budgets: each plugin declares a CPU budget per channel at
  48 kHz; `plugin_checks!` perf cases fail a release build over budget.

## Order

1. **F1–F2** (FFT, convolution) and **R1–R2** (one reference harness,
   ngspice in CI): the most-used gap and the loop everything else
   is verified with. Then **K1–K6** (architecture), before new families land.
2. **N1–N3** (netlist, DK method, solve strategies) with **R3–R4**.
3. **U1–U5** (unit types), before the library grows further, so new APIs
   are born typed.
4. **E1–E6** (BJT, FET, pentode, op-amp, OTA, diode presets) on N2.
5. **A1–A4** and **R5** (anti-aliasing for circuits, with budgets).
6. **P1–P3, P5** (datasheet as data, deterministic perf CI, flamegraphs).
7. **M1–M4** (neural inference, grey-box, capture).
8. **S1–S7**, **D1–D4**.
9. **H1–H9** (hardware beyond circuits) and **G1–G5** (design tools).
10. The exploratory items: **N7**, **M5**, **M6**, **E10**, **H10**.
